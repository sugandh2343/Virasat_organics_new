# Phase 4.3 — Static checkout UI

## Delivered
/checkout now redirects guests to /login?returnTo=%2Fcheckout. Explicit demo continuation returns to checkout; identity remains unverified.

The checkout has Delivery Address, Order Review, Payment Method and Confirmation stages. It reuses the existing session-scoped address service, shared address form, validation, location tools and cart selectors. Customers can add/edit/select addresses, change the default, and enter temporary delivery instructions. No address is considered geographically verified or serviceable.

Order review includes honest image placeholders, independent pack sizes, quantities, unit/line amounts and Edit Cart. Shipping/tax remain unconfigured publicly; final total and placement are blocked when any necessary values are missing. COD is selected only when enabled. Online Payment is disabled and labelled Coming Soon.

The ivory/forest/gold layout uses a desktop sticky summary and mobile stacked panels, native radio controls, modal focus management, step-heading focus, inline address errors, live feedback and the existing global reduced-motion rules.

## Isolation and order state
All five actual catalogue products remain Coming Soon with null prices and stock. Public checkout cannot submit orders.

Development-only preview: http://127.0.0.1:5174/dev/checkout
1. Choose Start isolated demo session.
2. Add a synthetic address with the shared address form, then select its radio.
3. Continue through review and COD.
4. Place Demo Order creates a DEMO-prefixed reference in memory.
5. Reset illustrative cart supports another test; End demo session discards addresses/orders.

This route is lazily imported only when import.meta.env.DEV is true. Its fixture has distinct sample IDs, visibly illustrative prices/stock/charges, and a nested instance of the existing StorefrontProvider. It never modifies public product services or public cart/session state. It does not read, write or synchronize localStorage. The production JavaScript is tested for absence of the route and sample data.

The existing reducer validates placement against current state, creates an immutable order snapshot and clears the fixture cart in one action. A UI submission lock plus idempotent request IDs prevent duplicates. A second different request against the cleared cart fails. Invalid/stale sessions, incomplete addresses, unavailable products, invalid quantities, missing prices/charges and non-COD payment are rejected.

Orders live only in session.orders. They are not persisted or sent to a server and disappear on refresh/logout. /order-success/:orderId resolves only an existing owned demo order. The isolated preview uses /dev/checkout/order-success/:orderId to retain its isolated provider. Missing/foreign references show an unavailable state. View Demo Orders leads to an explicitly unfinished history screen; order history and tracking are reserved for Prompt 4.4.
