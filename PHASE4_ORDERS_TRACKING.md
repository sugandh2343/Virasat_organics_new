# Phase 4.4 — Demo order history and tracking

## Functionality and data flow
/account/orders uses the existing account layout with reference search, all seven status filters, newest/oldest sorting, result counts and honest empty states. Order cards show demo reference/date, item quantities, known total, COD, demo payment status and current order status.

/account/orders/:orderId shows item and address snapshots, phone, instructions, configured totals, payment information, recorded history and an accessible tracking timeline. Unknown and foreign-session IDs show an unavailable state.

/account now shows recent demo orders, total count and latest status. Checkout confirmation links to both history and the exact detail record, including after cancellation. No hardcoded order copies or seeded customer purchases were introduced.

All reads use getSessionDemoOrders/getSessionDemoOrder from the existing checkout service. Both customerId and sessionId must match the current unverified demo session. session.orders remains the sole store; refresh/logout discards it, and localStorage never includes orders or addresses.

## Order contract
New placements record:
orderId, id (compatibility alias), customerId, sessionId, demo, createdAt, status,
statusEvents[{id,status,occurredAt,note}], items[], deliveryAddressSnapshot,
subtotal, shipping, tax, total, paymentMethod, paymentStatus, deliveryInstructions.

Legacy address/instructions aliases remain compatible with checkout. Items/media and address values are copied at placement. Later catalogue/address edits and cancellation do not rewrite historical snapshots. COD payment status is explicitly Not collected (demo).

## Tracking and cancellation
Only explicit statusEvents mark stages as recorded. A later status does not fill in earlier milestones. Missing timestamps are labelled Date not recorded. The placement event uses the actual local placement time; cancellation uses the actual local cancellation time. There are no fabricated shipping events, estimates, GPS positions or payment confirmations.

Cancelled is a separate terminal branch, never a delivered stage. Only Placed/Confirmed orders without later-stage history are eligible for local cancellation. The confirmation dialog explains that no business cancellation/refund occurs. The reducer checks ownership/current eligibility and adds one event; repeated cancellation returns the unchanged record. Keep/Escape uses the existing dialog focus restoration; successful cancellation focuses the detail heading.

## Reorder
Reorder revalidates every historical item against the current catalogue, configured selling price, status, stock and existing cart quantity. It is all-or-nothing, capped by stock and the existing 99-unit limit. Missing, inactive, Coming Soon, out-of-stock or insufficient-quantity items disable reorder with a reason. The reducer rechecks before adding current products to the existing cart. Reorder never creates an order or restores historical pricing.

## Limitations / future integration
No durable persistence, live delivery, Firebase authentication, payment capture, admin management or external API was added. Status advancement is not automatic: checkout creates Placed and explicit cancellation creates Cancelled. Other stages render only when actual demo events are supplied; tests use isolated synthetic events.

Future PHP/MySQL endpoints must authenticate ownership, validate order and cancellation rules server-side, preserve immutable snapshots, provide idempotent writes and authoritative status histories, and revalidate prices/stock for reorder. Payment capture/refunds and carrier tracking need separate verified integrations. Current demo session IDs are UI isolation, not security credentials.

No old website edits, deployment or commit.
